# M1 Mission Charter — Semantic substrate

## Outcome

Implement the smallest working Spectacular v2 substrate through two linked Markdown records,
representatively Proposal → Mission. Prove stable UUIDv7 identity, semantic Markdown round-trip,
typed linking, normalized SHA-256 fingerprints, deterministic lookup, and refusal of invalid
identity or relationship states.

## Record contract

The only universally required Spectacular record fields are:

```yaml
type: Proposal
id: <canonical-UUIDv7>
```

Proposal and Mission authoring defaults are `title`, `description`, `status`, `created_by`,
`created`, and `updated`. They are not universal identity requirements; when present in a known
grammar, their values are parsed and validated. Unknown valid properties are preserved without
gaining semantic authority. Tags are not generated by default.

The M1 Mission fixture links to its Proposal using:

```yaml
source: "Proposal:<canonical-UUIDv7>"
```

Paths are mutable addresses rather than identity. M1 supports exact lookup by UUID and complete
workspace-relative path. Bare-name and fuzzy lookup are deferred.

## Canonicalization and fingerprints

Canonical records use UTF-8, LF endings, stable known-field ordering, deterministic unknown-field
ordering, one terminal newline, and preserved frontmatter values and Markdown body. Property order,
equivalent YAML quoting, and CRLF/LF differences do not change the fingerprint. A changed known or
unknown value, relationship, or body does. YAML comments and byte-identical formatting need not be
preserved.

Fingerprints are computed from normalized content and are not stored as frontmatter authority.

## Owned paths

```text
v2/go.mod
v2/go.sum
v2/internal/domain/
v2/internal/workspace/
v2/internal/index/
v2/testdata/m1/
```

No other path is owned.

## Package authority

- `domain`: identity, Proposal/Mission semantics, typed references, static status validation, and
  refusal errors.
- `workspace`: Markdown/frontmatter parsing, unknown-property preservation, normalization,
  fingerprints, and atomic persistence.
- `index`: deterministic identity/path lookup and relationship validation.
- `testdata/m1`: approved positive and negative proof fixtures.

M2 may consume the Domain and Workspace APIs. M3 may build richer discovery over Index. M1 does not
implement governed lifecycle operations, authorization, evidence sufficiency, assessment,
reconciliation, CLI/Skill behavior, Guardrails, providers, caches, release, or migration.

## Delivery envelope

Central orchestration has activated M1 and may create an isolated worktree and
`codex/feat/v2-semantic-substrate` from the verified activation baseline. The executor may modify
only the owned paths, run local formatting/build/test and disposable fixture operations, add only a
UUIDv7 library and YAML v4 library, pin their resolved versions, and create at most three coherent
local checkpoint commits.

Pushes, PRs, tags, releases, provider changes, v1/root implementation edits, real workspace
migration, and M2/M3 work are forbidden.

Go 1.26 with the locally available toolchain is the current implementation recommendation. Exact
toolchain and dependency versions remain activation-time Type-2 pins, not product authority.

## Milestones

1. Establish the Go module and Domain types.
2. Implement canonical Markdown reading, preservation, fingerprinting, and safe writing.
3. Implement deterministic lookup and relationship refusals.
4. Complete integrated proof and independent boundary review.

## Evidence contract

Required scenarios:

- approved Proposal and Mission round-trip;
- canonical UUIDv7 validation;
- unknown-property and Markdown-body preservation;
- stable fingerprints across property order, equivalent quoting, and line endings;
- changed fingerprints for changed meaning;
- rename-safe identity lookup and relationships;
- discovery-order-independent index results;
- duplicate-ID, broken-target, and wrong-target-type refusal;
- failed-write preservation of the original file.

Required checks from `v2/`:

```text
gofmt -l .
go mod verify
go vet ./...
go test ./internal/domain ./internal/workspace ./internal/index
go test -race ./internal/...
go test ./...
go build ./...
```

Race testing may be marked unsupported only with direct host evidence. A reviewer who did not
implement M1 must independently inspect the binding contracts, final diff, package boundaries,
fixtures, and primary results.

## Retry and recovery

The Mission permits the initial implementation plus at most two focused repair rounds. Each repair
requires a new hypothesis and materially narrower action. The recovery point is the verified
activation baseline plus the last green local checkpoint. Preserve failed evidence and worktree
state; do not use destructive reset.

## Stop conditions

Stop on baseline or branch drift; need for another path or dependency; unknown-field/body loss;
inability to protect the original on failed persistence; duplicate authority or M2/M3 leakage;
authoritative persistent/generated output; v1 compatibility or migration work; toolchain/dependency
conflict outside the envelope; exhausted proof budget; blocking independent-review finding; or any
required remote/provider effect.

## Terminal return

Return `spectacular.handoff-return.v2` with final commit/tree, changed files, pinned dependencies,
check results, scenario evidence, independent-review findings, repair history, recovery point,
deviations, conflicts, and one central next action. The executor may not accept M1 or activate M2.
